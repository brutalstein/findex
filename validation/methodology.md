# Methodology

All measurements drive the real release binary (`cargo build --release -p
findex`) or the official `claude` CLI as subprocesses. Each Findex process
gets its own `LOCALAPPDATA` so no run shares index state with another, with
the operator's real Findex data, or with another system under test.

## Systems compared

| Label | What it is |
|---|---|
| `gitgrep` | Scripted lexical baseline: `git grep -n -I -i -F` with every query term, restricted to the same admitted files as Findex. Files ranked by best single-line term coverage, then matching-line count, then path. Approximates a careful agent using grep. |
| `findex-baseline` | `findex.exe` built from `44f1a38` (start of this work), `findex_search` over MCP |
| `findex-current` | This branch's `findex.exe`, `findex_search` over MCP |
| `findex-current-symbol` | This branch, `findex_find_symbol` (exact-symbol queries only) |

## Retrieval benchmark

* **Dataset.** `harness/golden.py` builds `golden/symbol_navigation.jsonl`
  (642 queries over 7 pinned corpora) with regular-expression definition
  finders that do not share code with Findex's Tree-sitter extractor, so the
  labels are not produced by the system under test. Query types:
  * `symbol_exact` (280): a defined name with at most two definitions; expected
    answers are the definition locations.
  * `identifier_words` (239): the same name split into lowercase words
    (`GitignoreBuilder` -> `gitignore builder`), as a user would phrase it.
  * `line_terms` (123): three rare words that co-occur on exactly one source
    line; that line is the expected answer. These are non-definition queries.
* **Split.** `sha256(corpus:name) % 10 < 3` -> `heldout` (~30 %). Ranking
  changes in this branch were tuned only on `dev`; `heldout` is reported
  separately to expose overfitting.
* **Metrics** (per query, then averaged): file Recall@1/5/10, file
  Precision@k over distinct files, MRR, nDCG@10, span Recall@k (path and line
  within ±1), missing-evidence rate, top-1 false-positive rate, evidence
  validity (the returned excerpt equals the cited line on disk), payload bytes,
  estimated tokens (`bytes / 4`, a heuristic, not a tokenizer), latency
  (nearest-rank p50/p95/p99).
* **Limitation.** Labels were generated by the agent that also changed the
  ranking and were spot-checked, not reviewed line by line by a human.

## Performance

* Cold index: fresh state directory, `findex index`, repeated `--reps` times
  (default 3). Peak working set, CPU time and I/O bytes are sampled from the
  process every 20 ms with `psutil`. A second `findex index` measures no-op
  reconciliation.
* Warm MCP latency: one long-lived `findex mcp` process answers up to 120
  golden queries per corpus through `findex_search` and `findex_find_symbol`.
  Idle CPU is sampled over 10 s after the last request.
* Watcher workload (ripgrep copy): real filesystem edits, creates, atomic
  renames and deletes; each is followed by a search that must reflect it.
* Concurrency: four MCP servers on one shared index database query in
  parallel.
* Timings on a developer laptop are noisy. Baseline vs current comparisons
  use the same corpus, machine and session, and are flagged as regressions
  only when worse by more than 10 %.

## Security and reliability

`harness/security.py` runs black-box checks against the release binary:
adversarial MCP frames (2 MiB line, invalid JSON, deep nesting, batches),
path-escape attempts (`..`, drive, `\\?\`, UNC, ADS, device names, NUL),
credential redaction in excerpts, `.env` admission, prompt-injection text
returned only as data, protocol version negotiation, no sockets opened during
indexing or serving (sampled every 10 ms), file symlink escape, corrupt
database rebuild, random SCIP and mutated LSP inputs, and killing the indexer
mid-run followed by recovery and `PRAGMA integrity_check`.

## Claude Code integration

`harness/claude_integration.py` starts real non-interactive `claude -p`
sessions (Haiku, small `--max-budget-usd`) in a fresh git-initialised copy of
the findex corpus:
1. explicit `--mcp-config` through `harness/mcp_trace_proxy.py`, which logs
   protocol metadata only (method, id, versions, tool name, sizes, error
   code), never arguments or results;
2. `--plugin-dir` with `findex.exe` on `PATH`;
3. the `findex claude` launcher.
Each run checks connection, tool discovery, a real `tools/call`, and that the
answer matches the known definition location.

## Claude Code A/B token study

* **Arms.** A: built-in tools only. B: the same tools plus the Findex MCP
  server (current build). Nothing else differs.
* **Controls held equal:** model and effort, prompt text, corpus commit,
  `--max-turns`, `--max-budget-usd`, allowed built-in tools
  (`Read, Grep, Glob, Edit`), denied tools (`Bash, WebFetch, WebSearch, Agent,
  Task, NotebookEdit, Write`), `--setting-sources project,local` (the
  operator's user hooks, plugins and memory are excluded),
  `--no-session-persistence`, fresh workspace and Findex state per session.
* **Order.** Counterbalanced: ABBA across tasks and repetitions.
* **Correctness** is judged by scripts, never by the model: definition
  location within ±1 line; caller file set recall and precision >= 0.8 vs
  `git grep`; required identifiers in the explanation; `cargo test` of the
  existing unit test after a bug fix; a hidden acceptance test appended after
  a feature edit.
* **Recorded per session** from `--output-format stream-json`: input, output,
  cache-creation and cache-read tokens, Claude Code's client-side cost
  estimate, turns, tool and MCP calls, files read, tool-result bytes,
  wall-clock time.
* **Primary metric** is total tokens (all four token classes). Cost is
  secondary: prompt-cache reuse spans sessions on the same account, so
  whichever arm runs second can read the shared system prompt from cache.
  Counterbalancing spreads that effect across arms but does not remove it.
* **Uncertainty.** Mean, standard deviation and a normal-approximation 95 %
  half-width per arm, plus paired (task, repetition) B - A differences. With
  three repetitions these intervals are wide; they are reported, not hidden.
* OpenTelemetry export was not used: stream-json already provides per-session
  usage, and enabling telemetry would need user-level settings that the study
  deliberately excludes.
